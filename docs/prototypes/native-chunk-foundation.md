# 原生材质分区基础

## 阶段结论

本阶段只建立 C++20 `sim_core` 的存储与批传输基础，不代表玩法模拟已经迁移。Godot Demo 仍运行并权威维护现有 GDScript 材质世界；仓库尚未引入 `godot-cpp`，也没有可用的 GDExtension 桥接实现。

## 已实现边界

- 一个字节一个 cell 的连续 row-major 存储，材质 ID 与 GDScript 的 `AIR..METAL` 严格对应 `0..9`。
- 世界宽高、区块尺寸、固定步频率、显式种子和初始材质均进入配置与快照。
- 默认区块为 64 × 64；右侧和底部边缘区块只传输其有效宽高与紧凑 cell 字节，不补齐到 64 × 64。
- `submit_command_batch` 一次按输入顺序应用一组命令。目前包含圆形绘制与圆形采掘，采掘只移除并统计 rock、sand、metal。
- `consume_dirty_chunks` 一次按 chunk row-major 顺序返回所有变化区块；同一区块每批只出现一次，消费后清除脏标记。
- `step` 以固定调用推进 tick；seed、随机状态、tick 与 cell 数据进入快照和确定性 checksum。

批命令在任何写入前整体验证材质 ID，避免非法传输导致半批状态。只在 cell 值实际改变时标记区块，重复绘制相同值不会产生虚假上传。

## 明确未实现

- 未迁移砂、水、气体、火焰、熔岩、温度、反应或重力场规则。
- 未实现激活区块调度、休眠或降频。
- 未设计存档兼容格式；当前 snapshot 是进程内值对象，不是冻结的持久化协议。
- 未接 GDExtension，Godot 不会读取这里的脏区块。
- 当前随机状态被纳入确定性状态，但存储阶段的 `step` 不消费随机数。

## 验证与基准

单元测试覆盖配置拒绝、材质 ID、批内顺序、边界圆裁剪、采掘统计、非整块边缘、脏批消费、确定性与 tick。

`starfall_native_chunk_benchmark` 使用 1024 × 1024 世界、64 × 64 区块和 2,048 个确定性圆形绘制命令，报告命令批耗时、脏区块数量、传输字节量、脏批消费耗时与最终 checksum。它用于记录趋势，不设置不稳定的 CI 硬阈值。

## 下一步接入顺序

1. 冻结 bridge DTO 的字节布局与版本字段。
2. 引入固定版本 `godot-cpp`，在单个物理步前提交命令批，在步后获取脏区块批。
3. 先做 C++/GDScript 双跑校验，再切换权威所有权，避免一次性替换导致难以定位的玩法偏差。
4. 逐类迁移运动与反应规则，并为每类规则增加确定性重放与性能基准。
